## 2. Rulings: the design of record for the gate queue (the hq sitting's, reversible; refuted once before code)

1. **Verbs.** `gate run <repo> [--session SID] [--lock PATH]... [--wall SECONDS] [--label TEXT] [--wait] -- <command...>` enqueues and prints `queued <id> position <n> repo <realpath> caller <sid-short or none>; result <state>/gate/<id>/result.json`, exit 0. `gate wait <id> [--timeout SECONDS] [--json]` polls at 5 s for `result.json`, prints `gate <id> <repo>: exit <code> in <m> min; log <path>`, exits 0 whatever the code (entry 25), 2 for an unknown id, 1 on timeout. `gate status [--json]` prints `running <id> <repo> since <HH:MM> <label>`, `queued <id> <repo> position <n> [waits on lock PATH]`, the last five `done <id> <repo> exit <code> <m> min`, then `runner: pid <n> since <HH:MM>` or `runner: none`. `serve` is internal. The command runs in `<repo>` as argv under the environment stored in its entry; the mutex key is the realpath (S38 runs one entry at a time and records the key; fix 3 flips to one per key). The tool reports exit codes and judges none.
2. **Queue and runner.** Entries are `<state>/gate/queue/<id>.json` (id, repo, command, env, locks, wall, label, caller, queued), mode 0600, written then renamed; the id is `YYYYMMDD-HHMMSS-<counter>`, the counter taken under `flock(<state>/gate/queue.lock)`. `run`, `wait` and `status` each spawn `serve` detached when the queue is not empty (`sys.executable -m claude_session gate serve`, never PATH; a new session, `close_fds=True`, stdio to `<state>/gate/runner.log`). `serve` takes `flock(<state>/gate/runner.lock, LOCK_EX | LOCK_NB)`, exits 0 if another holds it, else writes `runner.json` (pid, since, running, pgid) and loops: the oldest entry none of whose `locks` paths exists starts (a younger unlocked entry may run first); a head entry locked past `wall` seconds gets exit 126 `lock wait cut`; the entry runs in its own process group, output merged into `<state>/gate/<id>/log`, cut at `wall` (default 5400) by group SIGTERM then SIGKILL, exit 124; `result.json` (id, repo, command, exit, started, ended, seconds, log, caller, cut) is written last, atomically; the entry leaves the queue. After 60 s idle the runner removes `runner.json`, releases the lock, rescans, retakes it if an entry appeared, else exits. Results over 14 days old are pruned. A `serve` finding a stale `runner.json` (the flock proves its runner dead) kills that pgid (SIGTERM, then SIGKILL) and writes exit 125 `runner died` for its entry first. The queue is per state root; the docs say so.
3. **Caller and message.** The caller is `--session SID` (checked against `_SID` before any path join), else `$CLAUDE_CODE_SESSION_ID`, else none; no cwd match. On a result the runner writes `<state>/sessions/<caller>/inbox/<id>.json` (at, kind, id, repo, exit, seconds, log). The UserPromptSubmit and PostToolUse hooks, main thread only (an `agent_id` skips), before the posture-off return, take at most three inbox files by atomic rename into `inbox/read/`, print each as one `additionalContext` line (the `wait` line's text), then `<n> more: agentik session gate status` if any remain; under `MAX_OUT`, proved with ten files. The recommended wake is `gate wait <id>` in a background Bash with a timeout above the gate's length. No messaging socket is written.
4. **ntfy.** `gate` joins `resolver.SECTIONS` with `ntfy_url`, `ntfy_topic` and `wall` (default 5400); the runner reads the user layer alone, since it serves every repo. With both keys set the runner POSTs the result line to `url/topic` (`Title: gate <repo>: exit <code>`, 5 s timeout) once per result; a failure is one line in `runner.log`. Tests use the faked POST of §3, never a host.
5. **Docs.** README and source: the verbs in "Commands and skills" and a section "The gate queue" (why; `run` then `wait` in a background Bash or the hook's line; `--lock`; what 2, 124, 125, 126 mean); RUNBOOK the same with the state layout; SKILL.md "Other verbs"; `plugin/commands/gate.md` runs `agentik-session gate status`; `design/gate-r1.md` holds this section verbatim with a change log.
